## Upgrade policy

> [!WARNING]
> **Seamless (in-place) upgrade of the Spyre Operator is NOT supported.**
> Do not upgrade by switching the operator subscription channel/version or by letting the Operator Lifecycle Manager (OLM) upgrade the operator automatically.
> To move to a new version, you must **clean up the existing Spyre resources, uninstall the currently installed version, and then install the new version from scratch**.

Reasons for this policy:

- API schemas (CRDs) of `SpyreClusterPolicy` and `SpyreNodeState` and the resources generated by the operator (DaemonSets, Deployments, `DeviceClass`, `ValidatingAdmissionPolicy`, etc.) may change between versions, and stale resources are not migrated automatically.
- Switching the allocation mode (e.g., device plugin `classic` ↔ `dra`) requires that no workload holds a device allocation. See [SpyreClusterPolicy Customization](cluster-policy-customization-guide.md).

Expect the following during an upgrade:

- **Spyre workloads are interrupted.** Workloads using Spyre devices must be stopped before the cleanup.
- **Spyre devices are unavailable** from the moment the `SpyreClusterPolicy` is deleted until the new installation becomes `ready`.
- **Spyre-related state is rebuilt** (e.g., `SpyreNodeState`, which is regenerated by the new operator).

## Before you begin

- Read the release notes of the target version (see [Release Notes](../release-notes/v1.4.0.md)) and check whether the `MachineConfig` manifests, dependent operators, or required OpenShift version changed.
- Schedule a maintenance window. Make sure no user workload is using Spyre devices.
- Make sure you have `cluster-admin` privileges.

## Step 1: Back up the configuration

Save the current `SpyreClusterPolicy` so you can re-apply your customization after the new version is installed. Do not re-apply the saved file as it is; compare it with the schema of the new version first, as fields may have been added, renamed, or removed.

```shell
oc get spyreclusterpolicy spyreclusterpolicy -o yaml > spyreclusterpolicy-backup.yaml
```

If you manage other Spyre-related resources yourself (e.g., custom `ResourceClaimTemplate` objects, workload manifests), keep their manifests as well.

## Step 2: Stop Spyre workloads

Delete or scale down every workload that requests Spyre devices (extended resources `ibm.com/spyre_pf*` / `ibm.com/spyre_vf*` or DRA `ResourceClaim`/`ResourceClaimTemplate` with a Spyre `DeviceClass`) in all namespaces.

```shell
# Example: list Pods that have a Spyre resource request or a resource claim
oc get pods -A -o json | jq -r '.items[]
  | select((.spec.containers[].resources.limits // {} | keys[]? | startswith("ibm.com/spyre"))
           or (.spec.resourceClaims // [] | length > 0))
  | "\(.metadata.namespace)/\(.metadata.name)"'
```

Wait until all of these Pods are terminated.

## Step 3: Clean up and uninstall the current version

Spyre resources must be cleaned up **while the operator is still installed**. Once the operator is uninstalled, nothing reconciles these resources or clears their finalizers, so deletion may hang or leave stale objects behind.

Choose one of the following options.

### Option A: Using the Makefile

Run the `uninstall-operator` target of the Makefile in the [spyre-operator repository](https://github.com/ibm-aiu/spyre-operator), from a clone of the version that is currently installed. The target ensures that all custom resources are deleted before the operator is uninstalled.

```shell
make uninstall-operator
```

> [!NOTE]
> Check the Makefile of the cloned version for the variables the target requires (e.g., namespace) before running it.

Then confirm that the operator Pod is gone and that no Spyre CRD remains. OLM does **not** delete the `CustomResourceDefinition` (CRD) objects of an uninstalled operator, so delete any that remain.

```shell
oc -n spyre-operator get pod
oc get crd | grep spyre.ibm.com
```

### Option B: Manual cleanup

1. **Delete the `SpyreClusterPolicy`.** The operator removes the components it controls (device plugin / DRA driver, card management, metrics exporter, health checker, secondary scheduler, webhook validator). Confirm that only the operator Pod remains in the operator namespace (`spyre-operator` by default).

    ```shell
    oc delete spyreclusterpolicy spyreclusterpolicy
    oc -n spyre-operator get pod
    ```

    If the deletion is blocked or hangs, check the operator logs (`oc -n spyre-operator logs deploy/spyre-operator`) before taking further action.

2. **Delete `SpyreNodeState` and other custom resources.**

    ```shell
    oc get spyrenodestate
    oc delete spyrenodestate --all
    ```

    Also check whether any other Spyre custom resource instance remains.

    ```shell
    oc get crd | grep spyre.ibm.com
    oc get <resource-name> -A
    ```

3. **DRA resources (only if the DRA driver was used).** Confirm that the operator-created cluster-scoped resources are removed.

    ```shell
    oc get deviceclass | grep spyre
    oc get validatingadmissionpolicy,validatingadmissionpolicybinding | grep block-restricted-device-classes
    ```

    Confirm that **all** `ResourceSlice` objects published by the Spyre DRA driver (driver `spyre.ibm.com`) are gone for every node. The result must be empty. If any remains after the DRA driver Pods are gone, delete it.

    ```shell
    oc get resourceslice --field-selector spec.driver=spyre.ibm.com
    oc delete resourceslice --field-selector spec.driver=spyre.ibm.com
    ```

4. **Webhook configuration (only if the webhook validator was used).** Confirm that no stale webhook configuration remains. A stale webhook can block Pod or `SpyreClusterPolicy` creation after reinstallation.

    ```shell
    oc get validatingwebhookconfiguration | grep -i spyre
    ```

5. **TLS secret and certificates.** Confirm that the TLS secret `spyre-cert` and the cert-manager resources that issue it are removed from the operator namespace. The secret is used by the health checker and the DRA driver for mutual TLS, and is issued through cert-manager. A stale secret or certificate can be reused by, or conflict with, the new installation if the operator namespace is kept.

    ```shell
    oc -n spyre-operator get secret spyre-cert
    oc -n spyre-operator get certificate,issuer | grep -i spyre
    ```

    If any remain, delete them. Deleting a cert-manager `Certificate` does not delete its secret by default, so delete the secret explicitly.

    ```shell
    oc -n spyre-operator delete certificate <certificate-name>
    oc -n spyre-operator delete issuer <issuer-name>
    oc -n spyre-operator delete secret spyre-cert
    ```

6. **Uninstall the operator** once no Spyre resources remain.
    - **OpenShift web console**: `Ecosystem > Installed Operators` (or `Operators > Installed Operators` in OpenShift 4.19 or earlier), select the `spyre-operator` project, open the `IBM Spyre Operator` menu, and click `Uninstall Operator`.
    - **CLI**: delete the `Subscription` and the `ClusterServiceVersion` of the operator.

        ```shell
        oc -n spyre-operator get subscription,csv
        oc -n spyre-operator delete subscription <spyre-operator-subscription-name>
        oc -n spyre-operator delete csv <spyre-operator-csv-name>
        ```

    Confirm that the operator Pod is gone.

    ```shell
    oc -n spyre-operator get pod
    ```

7. **Delete the CRDs.** Uninstalling an operator through OLM does **not** delete its `CustomResourceDefinition` (CRD) objects. Delete them so that the new version installs its own CRDs from a clean state.

    ```shell
    oc get crd | grep spyre.ibm.com
    oc delete crd <crd-name>
    ```

8. **(Optional) Delete the operator namespace** if you want a completely fresh namespace.

    ```shell
    oc delete project spyre-operator
    ```

> [!IMPORTANT]
> Do **not** delete the `MachineConfig` / `MachineConfigPool` objects applied for SELinux, kernel parameters, PCI ACS, or VF start, and do not delete the dependent operators (cert-manager, NFD, secondary scheduler operator) as part of the upgrade, unless the release notes of the target version require changes. Removing or changing `MachineConfig` makes the Machine Config Operator reboot the affected nodes.
> If the target version provides updated `MachineConfig` manifests, apply them as described in [Card Management](cardmgmt-guide.md) and wait until the `MachineConfigPool` is `UPDATED`.

## Step 4: Install the new version

Follow [Operator Simple Setup Instruction](simple-instruction.md) from "3. Spyre Operator Setup" to install the new operator version and create a new `SpyreClusterPolicy`.

Alternatively, use the `install-operator` target of the Makefile in the [spyre-operator repository](https://github.com/ibm-aiu/spyre-operator), from a clone of the **new** version, and then create a new `SpyreClusterPolicy`.

```shell
make install-operator
```

> [!NOTE]
> Check the Makefile of the cloned version for the variables the target requires (e.g., namespace, catalog source) before running it.

Re-apply your customization manually by referring to the backup from Step 1 and the [SpyreClusterPolicy Customization Guide](cluster-policy-customization-guide.md) of the new version.

## Step 5: Verify the new installation

```shell
oc get spyreclusterpolicy spyreclusterpolicy -o jsonpath='{.status.state}{"\n"}{.status.message}{"\n"}'
oc get spyrenodestate
oc -n spyre-operator get pod
```

The state of the `SpyreClusterPolicy` must become `ready`, and a `SpyreNodeState` must exist for each Spyre node. See [Daily Operation Guide](daily-operation-guide.md) to confirm the device list and the allocation status, and then restart your workloads.

If the installation does not become ready, see [Troubleshooting for Admins](troubleshooting.md).
